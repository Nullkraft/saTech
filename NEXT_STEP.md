  A plan is useful later, but right now the risk is ambiguity: what exactly does the host send, what exactly does the firmware print
  back, and what exactly counts as pass/fail. A storyboard is useful if you want to think like the technician, but it can stay
  lightweight.

  I would do these in order:

  1. Technician storyboard
     Write the human workflow in plain language: “technician connects board, loads technician firmware, enters fulltest <RFin> from
     host tool, watches reports for LO1, LO2, final amplitude.” This catches missing operational assumptions.
  2. Acceptance checklist
     Define what must be true for the full test to pass:
      - frequency plan derived from RFin
      - control pin pre-check completed
      - LO1 programmed
      - LO1 scope decode captured
      - LO1 decoded registers match expected
      - LO2 programmed
      - LO2 scope decode captured
      - LO2 decoded registers match expected
      - BK390A voltage read
      - voltage converted to dBm
  3. Console contract
     Decide the stable command and response contract that the host will use while the technician console firmware is loaded. The
     current recommendation is to keep technician console commands as plain text, but make full-test report output newline-delimited
     JSON: one complete JSON object per line.

     This avoids inventing a custom parser while still being manageable for Arduino `Serial.print()` output. It also allows partial
     and fail-early reports because each line is complete on its own.

     Example frequency-plan report records:

     {"type":"report_begin","report":"frequency_plan"}
     {"type":"value","name":"rfin_mhz","value":1735.113}
     {"type":"value","name":"lo1.frequency_mhz","value":5326.000}
     {"type":"value","name":"lo1.m","value":80}
     {"type":"value","name":"lo1.f","value":45}
     {"type":"value","name":"lo1.n","value":4095}
     {"type":"value","name":"lo1.diva","value":1}
     {"type":"report_end","report":"frequency_plan"}

     Example pass/fail check record:

     {"type":"check","name":"lo1_select","expected":"asserted","actual":"asserted","result":"PASS"}

     Example register records:

     {"type":"register","lo":"LO1","register":"R4","state":"DIRTY","expected":"0x638C803C","decoded":"0x638C803C","result":"PASS"}
     {"type":"register","lo":"LO1","register":"R5","state":"CLEAN","expected":"0x00580005","decoded":null,"result":"CLEAN"}

     The host should parse only the JSON report lines for full-test automation. Banners, help text, and ad hoc technician status text
     can remain human-readable as long as full-test report records are clearly JSON objects.

     Firmware implementation note: do not hard-code every JSON example as a literal string in firmware. Program flash is limited, so
     JSON report output should be generated by small reusable helper functions for each record type. For example, one helper for a
     `value` record such as `{"type":"value","name":"rfin_mhz","value":1735.113}` can also emit the related LO frequency, `M`, `F`,
     `N`, and `DIVA` records by changing the name and value arguments.

  4. Host orchestration outline
     Sketch the host-side sequence without coding yet:

     send RFin
     request/parse frequency plan
     run pin pre-check
     command LO1 program
     capture/decode scope
     compare LO1 expected vs actual
     command LO2 program
     capture/decode scope
     compare LO2 expected vs actual
     read BK390A
     convert voltage to dBm
     print final report

  5. Failure behavior
     Decide where the test stops versus continues. For example, if LO1 register comparison fails, do we stop immediately, or still
     attempt LO2 so the technician gets more information?

  My recommendation: start with the console contract and acceptance checklist. Those will force the useful decisions without dragging
  us into code too early.
